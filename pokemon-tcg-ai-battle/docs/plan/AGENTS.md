# 文章作成ルール（docs/plan/ 配下）

`docs/plan/` の設計書、実装仕様、実行計画、監査記録を作成・編集するときは、リポジトリルートの`AGENTS.md`（本ZIPには未収録）に加えて本規則へ従う。既存文書の言語は維持し、新規文書は特別な理由がなければ日本語で書く。

## 正典と文書の役割

- 文書間の優先順位は [MAGE_PTCG_v5_README.md](MAGE_PTCG_v5_README.md) を正とする。`bootstrap_kernel_implementation_plan.md`と`ai_orchestrator_implementation_plan.md`はdesign/implementation正典に従属し、MAGEのアルゴリズムやGate条件を再定義しない。
- 同じ仕様を複数文書へ複製しない。正典側に記載し、他文書からは節名またはアンカー付きリンクで参照する。
- 設計書には安定した仕様、実装計画には実装契約、オーケストレーター文書にはAI開発の状態・権限・承認、監査記録には確認結果と残課題を書く。現在の作業状況を設計仕様へ混ぜない。
- 仕様と実装が食い違う場合、文書だけを整合したように書き換えず、差異と解消方針を明記する。

## 構造

- 1 段落を 1 論点とし、各節・各段落は結論から始める。
- 節の冒頭に、その節で決めることまたは示すことを短く書く。
- 3 項目以上の並列、比較、対応関係は箇条書きか表にする。
- 依存関係、状態遷移、処理順が文章だけでは分かりにくい場合に限り、Mermaid 図を使う。図の直前に読み取るべき要点を 1 文置く。
- 実行ログ、長いコマンド、換算表など本文の主張に不要な詳細は付録または実験記録へ分離する。

## 簡潔さ

- 1 文へ複数の論点を詰め込まない。条件や例が長い場合は子箇条書きへ分ける。
- 同義反復や言い換えによる水増しをしない。表や図と本文が重複する場合、本文は結論だけに圧縮する。
- 既存節を直すときは、論点を無制限に足すより、重複を除いて境界を明確にする。
- 背景説明を各節で繰り返さない。初出箇所へ集約し、以後は参照する。

## 用語と記法

- API 名、型名、数式記号、ゲーム用語は正典と実装に一致させる。別名を導入する場合は必要性と対応関係を示す。
- 日本語の句読点は「、」「。」を使う。英数字、単位記号、コード識別子は半角とする。
- 見出し番号のある文書は既存の番号体系を維持する。改番時は本文、目次、相互参照を同時に更新する。
- 外部資料は一次情報を優先し、文書名またはページ名、URL、必要に応じて確認日を記載する。
- 時刻、回数、勝率、計算量、メモリ量などの数値には、条件と単位を添える。

## 根拠と主張

- 公式仕様、ローカルでの観測、設計上の選択、仮説、将来案を明確に区別する。
- 「最適」「保証」「改善」「初めて」などの強い表現は、適用範囲と検証根拠がある場合だけ使う。
- 実測結果には commit hash、設定、対戦数、seed、比較対象、評価方法を追跡できる形で添える。
- 単一 seed、少数対戦、Public LB の一結果は参考値と明示し、一般的な優位性へ拡大解釈しない。
- 未確定の値や仕様は `TODO:` または `(要検証)` とし、確定事項のように書かない。
- 外部要因で変わりうる Kaggle の規則、日程、提出制限は、公式情報の確認日を添える。

## 編集時の確認

- 正典の優先順位、見出し番号、相互参照、用語、コード例を壊していないか確認する。
- `design/00_overall_plan.md`と`design/05_evaluation_submission_and_strategy_plan.md`のGate名・期限が一致するか確認する。
- Bootstrap Kernel、完全版Orchestrator、MAGE本体の実装済み範囲を混同していないか確認する。
- 変更した主張が、実装・テスト・実験記録の根拠と一致するか確認する。
- 文書の全文整形や無関係な表現統一を同じ変更へ混ぜない。
- 未検証の性能や未実装の機能を、現在の能力として記述しない。
