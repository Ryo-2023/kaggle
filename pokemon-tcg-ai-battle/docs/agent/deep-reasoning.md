# 熟考プロトコル

非自明な設計、デバッグ、実験判断で使う。外部化するのは逐語的な思考ログではなく、検証可能な構造化判断メモとする。R1 以下は P1、P6、P7 の短縮版でよい。

## P0 深度と委譲

- `AGENTS.md` の R0〜R3 から深度を選び、理由を 1 行で示す。
- 検索、走査、集計、定型検査は、境界と出力形式を固定して最小十分な lane へ委譲する。
- 高い effort は、未整理の大量入力ではなく蒸留済みの判断へ使う。

## P1 問題の再定式化

- 依頼を自分の言葉で 1 文にする。
- 観測可能な成功条件を書く。
- 何が観測されたら失敗かという反証条件を書く。
- 今回扱わない範囲を書く。

## P2 前提台帳

- 前提ごとに `確実` / `推定` / `未検証` を付ける。
- `未検証` には確認方法を付ける。
- 未検証の前提だけに依存した結論を確定しない。

## P3 選択肢

- 実在する選択肢を 2〜3 案出し、各案の利点と損失を 1 行ずつ書く。
- 採用理由と不採用理由を書く。
- 実質的に 1 案しかない場合、偽の対案を作らず、その理由を示す。

## P4 段階実行

- 1 フェーズを 1 つの中間成果物または検証結果で区切る。
- フェーズ境界で P1 の成功条件とスコープを再確認する。
- 長い作業では、完了まで黙らず短い進捗を共有する。

## P5 反証

成果物を落とす reviewer の立場で、次を別節として確認する。

- 同じ結果を説明する代替仮説はないか。
- 端、空、最大、退化、タイムアウト時に崩れないか。
- バグやデータ取り違えでも同じ観測が出ないか。
- 比較条件、seed、情報境界、評価指標に穴がないか。

最後に、最強の反論、それが判断を変えるか、決着に必要な証拠を各 1 行で書く。R3 では可能なら別 provider の reviewer に依頼する。

## P6 検証と主張

- 検証前に「完了」「合格」「改善」と書かない。
- 数値には、コマンド、ファイル、実験記録のいずれかを添える。
- 桁、符号、単位、範囲、和、非負、正規化を確認する。
- 観測条件を越えて一般化しない。

## P7 決定メモ

- 決定と理由。
- 棄却した案と理由。
- 残った未検証前提。
- 次の action、owner、停止条件。

深く考え、短く書く。チェック項目を yes / no だけで流さず、前提が崩れたら推測で埋めず停止する。
