# 収集の長局欠損修正と resume の provenance 挙動（2026-08-04）

## 1. 長い対局が全滅していた不具合（修正済み）

2,000局の実収集で **142局（7.1%）が fault** した。全件の原因は同一である。

```
LocalDatasetV2Error: canonical JSON exceeds the node limit
  actor_pool_v1._game_record_content_hash_v1 -> canonical_json_bytes_v2 -> _validate_json_bounds
```

`MAX_CANONICAL_JSON_NODES_V2 = 100_000` に対し、成功した局の最大が **99,897ノード（74 transition）**
だった。すなわち **概ね 75 transition 以上の対局が全て捨てられていた**。

根本原因は上限の適用範囲の誤りである。この 100,000 は「未検証データセット由来の
**1決定分**の学習レコード」を縛るための値であり、`actor_pool_v1` はそれを
**1局まるごと**（数十 transition × 各々の model input と prefix steps）のハッシュ計算へ
流用していた。1局は正当に1〜2桁大きい。

### 実害はデータの偏り

fault はレーンに偏在した。対局が長いレーンほど失われた。

| レーン | 修正前 fault | 修正後 fault | transition（前→後） |
|---|---|---|---|
| `rocket_mewtwo_spidops` | 0/666 | 0/666 | 9,478 → 9,545 |
| `alakazam` | 18/667 | 19/667 | 10,668 → 10,686 |
| `grimmsnarl_froslass_munkidori` | **124/667** | **0/667** | 13,702 → **26,294** |

全体では **33,848 → 46,525 transition（+37%）**。失われていたのは長期戦の局面であり、
残ったデータは短い対局に偏っていた。学習データとしての欠陥であって、単なる取りこぼしではない。

### 修正方針

`canonical_json_bytes_v2` に `max_nodes` / `max_bytes` を追加した。**既定値は従来どおり**
なので未検証データ経路の防御は変わらない。ゲームレコードだけが専用の上限
（`MAX_GAME_RECORD_JSON_NODES_V1 = 2_000_000`）を明示的に渡す。共通の上限は緩めていない。

実装は commit `f0877472` に含まれる（コミット題名は進捗表示の話になっており、
この修正を指していない。追跡のためここに記録する）。

### 残る fault

`alakazam` の 19/667（0.95%）は `worker exited with code 1` のまま残っている。
原因は未解明。7.1% → 0.95% へ下がったが、ゼロではない。

## 2. resume がコード変更で無効になる（未対処）

再収集時に `resumed_skipped=0` となり、既存 1,858 局が再利用されず全2,000局が
収集し直された。ゲームディレクトリは 4,440 個（約2倍）へ膨らみ、約20分を要した。

原因は `derive_actor_job_id_v1` の入力に **`source_commit` が含まれる**こと。
`current_repo_commit_v1()` は `git rev-parse HEAD` を返すため、**コミットが1つ入るだけで
全ジョブIDが変わり、既存データが別物として扱われる**。

- 1回目: HEAD = `a21e1b8f`
- 2回目: HEAD = `f699d67b`

### 評価

provenance を固定する設計意図自体は正しい。異なるコードで集めた軌跡を黙って
混ぜないための仕組みであり、これを外すべきではない。

問題は **黙って全件再収集すること**である。run summary は `resumed_skipped=0` としか
言わず、「既存 N 局は別 source_commit のため再利用しない」と伝えない。利用者からは
resume が壊れたようにしか見えず、ディスクとCPU時間が二重に消費される。

### 次にやること

`collect-trajectories` が、出力先に別 `source_commit` の既存局を見つけたとき、
その件数と commit を集計出力へ明示する。再利用しない判断は変えない。

### 蓄積されたデータの実測（2026-08-04 追記）

再収集で膨らんだ `p0-rule-agent-2000/games` の中身を全件検査した。結論は
**データ品質上の問題はなく、学習に使える独立標本が約2.1倍に増えている**である。

| 観点 | 実測 |
|---|---|
| レコード数 / transition | 4,270局 / **87,258 transition**（直近1回の収集は1,981局・46,525） |
| 収集セッション | 4回（08-03 17時・18時・19時、08-04 05時） |
| `subject_behavior_version` | `b89ca316…` の**1種類のみ** |
| `engine_source_sha256` | `b9201330…` の**1種類のみ** |
| `content_hash` 重複 | **0件** |
| `(archetype, seat, seed)` の重複 | 1,862件 |
| そのうち transition 列が完全一致 | **0件** |

重複キー 1,862件はすべて**異なる決定列**を生んでいる。`engine_seed_supported: False`
（エンジンに再現可能な seed 供給経路がない）という既知の事実と整合する。すなわち
同じ `(archetype, seat, seed)` の再実行は複製ではなく**独立標本**である。

学習方策・エンジンが単一である以上、世代の異なる方策を混ぜてはいない。したがって
4,270局すべてを学習に使ってよい。resume が効かなかったことは**計算時間の無駄**では
あるが、**データ汚染ではない**。
